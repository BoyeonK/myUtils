# 문서 작성 규약

**같은 내용을 여러 곳에 중복해서 쓰지 않는다.** 어디에 쓸지의 기준은 **언제 읽어야
하는가**다.

| 내용 | 위치 |
|---|---|
| 이 줄을 바꾸면 무엇이 깨지는가 | 코드 주석 |
| 여러 파일에 걸친 시퀀스·상태표·락 규칙, 수명·소유권 관계, 컴포넌트별 함정 | `design/<컴포넌트>.md` |
| 컴포넌트를 가리지 않는 공통 제약 | `design/<주제>.md` (`threading.md`, `instrumentation.md`) |
| 세션이 시작할 때 항상 알아야 할 것 — 진입점, 빌드, 금지 사항 | `CLAUDE.md` |
| 정형화된 AI 개발 workflow의 단계와 실행 규칙 | `workflow.md` |
| 아직 정하지 못한 것 | `design/OPEN_QUESTIONS.md` |
| 완료 이력, 착수 가능한 TODO | `progress.md` |
| 프로젝트의 목적과 외부 사용법 | `README.md` |

## 보관하지 않는 것

**이 레포는 "왜 그렇게 정했는가"를 보관하지 않는다.** 기록하는 것은 **지금 무엇이 어떻게
동작하는가**와 **무엇을 건드리면 깨지는가**뿐이다. 검토했다 버린 대안, 당시의 판단 근거,
미래의 재검토 조건은 남기지 않는다.

그래서 변경할 때 **읽어야 할 문서가 적다.** 대신 현재 동작을 바꿀 때는 그 동작을 서술한
주석과 문서를 **같은 변경에서 함께 고쳐야 한다** — 뒤에서 맞춰줄 이력 문서가 없다.

예외는 `progress.md`다. 거기에는 "무엇을 했는가"가 날짜와 함께 남지만, 그것은 이력이지
현재 동작의 근거가 아니다. **현재 동작을 알기 위해 `progress.md`를 읽어야 하는 상태를
만들지 않는다.**

## `CLAUDE.md`는 부트스트랩 문서다

모든 세션이 **항상** 읽는 자리다. 그래서 크기 자체가 비용이다.

* **특정 컴포넌트에만 해당하는 규칙을 쓰지 않는다.** 컴포넌트 하나에만 적용되는 것은 그
  컴포넌트의 `design/*.md`로 보내고 여기서는 링크만 건다. 지금 건드리지 않는 컴포넌트의
  세부가 쌓이면 공통 규칙이 묻힌다.
* 여기 남는 것은 **어느 작업을 하든 필요한 것**뿐이다 — 무엇이 어디 있는지, 빌드하는 법,
  어기면 바로 깨지는 금지 사항, 모든 컴포넌트에 걸리는 설계 제약.
* 상세는 링크한 문서가 갖는다. **링크를 걸면 그 문서를 같은 변경에서 만든다.**

## 컴포넌트 스펙(`design/<컴포넌트>.md`)

* **"현재 동작 서술"을 통째로 옮기지 않는다.** 그게 가장 잘 낡는다. 한 파일 안에서
  설명되는 규칙은 코드 주석에 두고, **파일을 넘나드는 시퀀스와 수명·소유권 관계**만
  스펙에 둔다.
* **각 invariant는 자신을 검증하는 테스트 이름을 단다.** 테스트가 깨지면 스펙이 틀렸거나
  코드가 틀렸거나 둘 중 하나다. 이것이 문서 드리프트를 막는 유일한 자동 장치다.
* 정책 상수는 **값이 아니라 의미**를 적는다 — 무엇을 판정하는 값인지, 다른 상수와 어떻게
  상호작용하는지, 바꾸면 무엇을 먼저 측정해야 하는지.

## `design/OPEN_QUESTIONS.md`

여러 세션이 같은 문서를 보고 이어서 논의하는 공간이다. 참여 규칙(서명·날짜, 측정 대기
항목에 의견 쌓지 않기)은 파일 상단을 따른다.

**결론이 나면 그 결정을 코드 주석이나 `design/*.md`의 현재 동작 서술로 직접 반영하고
질문은 지운다.** 별도의 결정 기록 문서를 만들지 않는다.

`progress.md` TODO와의 경계는 **"오늘 바로 착수할 수 있는가"**다. 먼저 골라야 할 게
있으면 OPEN_QUESTIONS 쪽이다.

## 읽는 순서

설계 또는 구현 작업을 시작하기 전에는 `CLAUDE.md`의 "작업 시작 전" 절이 정한 순서를
따른다. 이 문서는 **쓸 때** 보는 것이고, 그쪽은 **읽을 때** 보는 것이다.
