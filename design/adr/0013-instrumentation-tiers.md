# ADR-0013 계측을 비용 3단으로 나누고, 비싼 것만 런타임 플래그로 끈다

- Status: Accepted
- Date: 2026-09-15

## Context

ADR-0003·0007·0008·0011·0012이 전부 "이 조건이 관측되면 재검토한다"는 재검토 조건을
달아두었다. 그런데 **그 조건을 감지할 수단을 만들어 두지 않았다.** 트리거는 정했는데
알람이 없는 상태였다.

필요한 지표를 빈도로 정리하면 이렇다.

| 지표 | 어느 ADR | 빈도 | 비용 |
|---|---|---|---|
| 살아있는 chunk 바이트 합계 | 0008 | chunk당 1회 | atomic 2회 |
| chunk 고정 시간 | 0007 조건 2 | chunk당 2회 | clock 2회 |
| 배치당 처리 메시지 수 | 0011 (budget 32) | 배치당 1회 | 증가 1회 |
| runnable 큐 대기 시간 | work stealing 판단 | 배치당 2회 | clock 2회 |
| Send 수락/거부 | 0012 Uncertainty | 메시지당 1회 | 증가 1회 |
| **mailbox mutex 대기 시간** | 0011 (contention) | **메시지당 2회** | **clock 2회 ≈ 40~50ns** |

64 KB chunk에 200바이트 패킷이면 chunk 하나가 320개 메시지를 담는다. **chunk당 clock
2회는 메시지당 0.15ns다.** 배치당도 32분의 1이다. 여섯 중 다섯은 사실상 공짜다.

## Decision

### 계측을 비용 3단으로 나눈다

```
1단  chunk·actor 수명 단위     항상 켠다
2단  배치·runnable 단위        항상 켠다
3단  메시지 단위 시계 읽기      런타임 플래그로 끈다
```

### 3단만 `MyUtils::SetProfilingEnabled()`로 제어한다

컴파일 타임 매크로를 쓰지 않는다. 기본값은 꺼짐이다.

현재 3단에 해당하는 것은 mailbox mutex 대기 시간 하나뿐이다.

## 근거

### 왜 "디버그 vs 릴리즈"로 가르지 않는가

전처리기로 계측 전체를 묶으면 **끌 이유가 없는 것까지 같이 꺼진다.** 그러면 정작
메모리가 이상해 보이는 순간에 "재빌드해서 다시 재현해야" 하는 상황이 된다.

재검토 조건들(메모리 압력, pool miss, chunk 고정)은 성격상 **운영 중에 보고 싶은
지표**다. 그때 재빌드·재배포할 수 없고, 재현하면 이미 상황이 다르다.

경계는 "디버그냐 릴리즈냐"가 아니라 **"비용이 실제로 드느냐"**로 그어야 한다.

### 왜 매크로가 아니라 런타임 플래그인가

3단이 감싸는 것이 `clock::now()` 두 번(40~50ns)인데, **런타임 분기 1ns 미만으로 그
95%를 없앨 수 있다.**

| | 컴파일 타임 매크로 | 런타임 플래그 |
|---|---|---|
| 꺼졌을 때 비용 | 0 | relaxed load + 예측되는 분기 ≈ 1ns 미만 |
| 켜는 방법 | **재빌드 + 재배포** | 호출 한 번 |
| 빌드 구성 | 2개 | 1개 |
| 코드 썩음 | **컴파일되지 않으면 조용히 썩는다** | 없음 |

나머지 1ns를 더 얻자고 빌드 구성을 둘로 늘리고, `#ifdef` 안의 코드가 아무도 컴파일하지
않는 사이 썩을 위험을 지는 건 수지가 맞지 않는다. **처음 켜는 날이 하필 급한 날이다.**

### 왜 플래그가 `relaxed`인가

이 플래그는 "지금부터 재면 좋겠다"는 힌트이지 다른 메모리 접근과의 순서를 요구하지
않는다. 켜는 순간 경계에서 몇 건이 새거나 빠질 수 있지만 통계 목적이라 무해하다.

### 왜 SendBuffer와 같은 TLS 패턴인가

hot path가 자기 thread의 블록만 만지므로 동기화가 없고, 블록의 생성자·소멸자가 등록과
집계를 처리하므로 thread가 죽어도 누적값을 잃지 않는다. [ADR-0009](0009-parts-not-framework.md)의
"스레드별 상태는 스스로 초기화한다"와도 맞는다.

## 기각된 대안

| 대안 | 기각 사유 |
|---|---|
| 계측 전체를 `#ifdef`로 | 끌 이유가 없는 것까지 꺼진다. 운영 중 관측이 불가능해진다 |
| 3단만 `#ifdef`로 | 얻는 게 1ns 미만인데 빌드 구성이 둘로 늘고 코드가 썩는다 |
| 3단을 1차에서 아예 제외 | mailbox contention은 ADR-0011이 명시한 재검토 조건이다. 비용이 플래그 하나라 지금 넣는 편이 낫다 |
| 계측 전부를 항상 켬 | 메시지당 40~50ns는 hot path에서 무시할 수 없다 |

## Consequences

- **재빌드 없이 재검토 조건을 판정할 수 있다.** 이게 이 ADR의 목적이다.
- 3단 프로브가 늘어나면 전부 같은 플래그를 공유한다. 세분화가 필요해지면 그때
  플래그를 나눈다 — 지금 미리 나누지 않는다.
- `LiveChunkCount() * DEFAULT_CHUNK_CAPACITY`로 메모리를 추정하던 부정확함이
  `LiveChunkBytes()`로 해소됐다([ADR-0008](0008-baseline-tuning-policy.md) Consequences).
- 테스트 실행 파일이 종료 시 통계 요약을 출력한다. 합성 워크로드라 절대값의 의미는
  제한적이지만, **계측이 살아 있다는 것 자체는 매 실행마다 확인된다.**
- `ProfilingFlagGatesMailboxProbe` 테스트가 "꺼져 있으면 누적되지 않고 켜면 누적된다"를
  검증한다. 플래그가 무력화되면 테스트가 잡는다.

## Uncertainty

3단에 넣을지 2단에 둘지 애매한 지표가 앞으로 나올 수 있다. 기준은 **메시지당 clock을
읽는가**이며, 그것만으로 애매하면 실제로 재보고 정한다.

계측 자체의 오버헤드는 측정하지 않았다. 1·2단은 증가 연산과 chunk/배치당 clock이라
무시할 수준으로 보지만 **확인한 것은 아니다.**

**Revisit when:** 1·2단 계측이 프로파일에 유의미하게 잡힐 경우.
